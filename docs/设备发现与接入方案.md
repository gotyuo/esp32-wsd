# EnvMon 设备发现 / 握手 / 多项目接入方案

版本：`20261006-v1.0`
适用固件：`TFT7735 2.0.0`（`esp32-4spi-st7735s-tft-v2.0.0`）

---

## 一、先说结论

| 你的疑问 | 结论 |
|---|---|
| 能不能在服务端加"握手"或采集端口？ | **能，而且固件早已支持一半**——它上电就会在多播组 `239.255.1.1:12091` 广播探针，只等服务端应答。你服务端缺的就是这个"应答者"。 |
| 不同项目设置不同，不可能靠默认值 | **对。根因是探针不带身份**（裸字符串 `ENVMON?`），服务端无从区分。解法是让探针携带 `pid`，服务端按 pid 下发**该项目专属**配置。默认的是**发现机制**，不该默认的是**项目参数**。 |
| 别的"自动采集"项目怎么拿设备信息？ | 业界通行的共同套路是：**先验身份 → 再下发配置 → 才允许上报数据**。差别只在身份载体和发现通道（见第五节对照表）。 |

## 二、固件里已经有什么（源码确证）

`firmware/esp32-7oled/src/net_mgr.cpp:471~569`：

```
多播组   : 239.255.1.1
端口     : 12091 (UDP)
设备发    : "ENVMON?"                      每 4 秒一次
服务应答  : {"ip":"...","port":18830,"user":"envmon","pass":"envmon"}
设备动作  : 写入 NVS → server_mode 置 1 → 重启 → 按该配置 MQTT/HTTP 上报
超时     : 45 秒无应答 → 退回 AP 配网门户
```

流程本身是对的：**发现 → 握手 → 下发配置 → 重启 → 上报**。
缺陷只有一条：**第一步的请求里没有身份**，所以服务端不知道"你是哪个项目的设备"。

## 三、改造方案（已实现并自测）

### 3.1 服务端：`services/beacon_server.py`

纯标准库，无需 pip。已实测通过的场景：

| 探针内容 | 服务端行为 | 实测结果 |
|---|---|---|
| `{"probe":"EnvMon","pid":"clinic-a","did":"esp32-4d3f54"}` | 查 `clinic-a` → 回它的服务器 | ✅ `{"ip":"192.168.2.220",...}` |
| `pid=clinic-b` | 查另一套配置 | ✅ `{"ip":"192.168.2.221",...}` |
| `pid=ward-101`（前缀匹配 `ward-*`） | 命中前缀规则 | ✅ `{"ip":"192.168.2.222",...}` |
| `pid=not-exist` | **静默不应答** | ✅ 6 秒无响应（项目隔离生效） |
| 裸 `ENVMON?`（旧固件） | `default` 为 null → 不答；填了才答 | ✅ 按配置受控 |

```bash
python beacon_server.py --config projects.json          # 常驻服务
python beacon_server.py --probe pid=clinic-a did=xxx    # 自测（模拟设备探一次）
```

配置文件 `projects.json`：

```json
{
  "projects": {
    "clinic-a": {"ip":"192.168.2.220","port":18830,"user":"envmon","pass":"envmon"},
    "clinic-b": {"ip":"192.168.2.221","port":18830,"user":"envmon","pass":"envmon"},
    "ward-*":   {"ip":"192.168.2.222","port":18830,"user":"ward","pass":"ward"}
  },
  "default": null
}
```

> `default` 保持 `null` 是关键：**多项目共存时必须关**，否则任何未登记设备都会被你家服务器认领。

### 3.2 设备侧：`services/beacon-project-id.patch.md`

改动 **3 处**（`#define PROJECT_ID` / 格式串 / 发送那一行），探针变成携带身份的 JSON。
本机无 espressif32 工具链，需你用 Arduino IDE 编译上传。

```json
{"probe":"EnvMon","pid":"clinic-a","did":"esp32-4d3f54"}
```

应答格式**完全不变**，固件的解析代码不用动。

### 3.3 兼容性（可灰度）

| 组合 | 行为 |
|---|---|
| 未打补丁旧设备 + 本服务端 | 发裸探针，开 `default` 则正常接入（单项目场景不用改固件） |
| 打补丁设备 + 本服务端 | 按 pid 精确路由 |
| 打补丁设备 + 旧服务端 | 旧服务端忽略内容照旧回 IP → 仍能连（退化为单项目） |

## 四、部署要点（踩坑预警）

| 坑 | 说明 |
|---|---|
| **Docker 多播收不到** | 必须 `docker run --network host` 或 compose `network_mode: host`。bridge 模式下多播出不去。 |
| **多网卡机器选错接口** | 服务器有多张网卡时，UDP 默认从主路由出口发。必要时在容器/主机指定路由或用 `IP_MULTICAST_IF`。 |
| **防火墙** | 放行 **UDP 12091**（入站），设备到服务器的 TCP 18830/12090 也要通。 |
| **跨网段/VLAN** | 多播 TTL 默认有限、二层隔离也挡多播 → 通常跨 VLAN 不通。多项目若分 VLAN，就需要第五节的"网关后端"思路。 |
| **应答里的 ip 要能被设备解析到** | 填设备真正能连到的地址（同网段可达），别填 127.0.0.1 或容器内部 IP。 |

## 五、业界"自动采集"是怎么做的（对照）

| 机制 | 通道 | 身份载体 | 典型用途 | 本项目是否适用 |
|---|---|---|---|---|
| **专用 UDP 多播 beacon** | UDP 多播 | 自定义负载 | 局域网设备自发现 | ✅ **固件现在就是这一种**，只需加 pid |
| **mDNS / DNS-SD（Bonjour）** | UDP 5353， `_srv._tcp.local` | SRV + **TXT 记录**携带元数据 | 打印机、HomeKit、Chromecast | ✅ 更标准，但 ESP32 要引库，固件改动大 |
| **SSDP / UPnP** | UDP 1900 HTTPU | USN/ST 类型 + XML 描述 | 智能家居、路由器、DLNA | ⚠️ 偏重，IoT 已少见 |
| **CoAP 资源目录（`.well-known/core`）** | UDP 5683 | `rt`/`if` 资源类型，支持 OSCORE 鉴权 | 受限设备、6LoWPAN 传感网 | 适合极低功耗，本项目偏重 |
| **DHCP Option / 路由器下发** | DHCP 报文 Option（如 224、自定义） | 租约里的厂商选项 | 企业内网自动配置 | 需控在自己路由器上 |
| **云端设备注册（Claim）** | TLS + 预置证书/密钥 | **Device ID + Claim Code**，云端先绑定账号再下发 endpoint | AWS IoT / Azure DPS / 阿里云一机一密 | ✅ **跨公网、多租户的标准答案** |
| **BLE / SmartConfig 配网** | 蓝牙或 Wi-Fi 混杂模式 | App 把 SSID/凭证/项目信息灌进设备 | 小米、涂鸦等消费 IoT | 需 App 配合 |

### 共同套路（画重点）

无论哪种，**合格的设备接入都是三段式**：

```
① 设备自报家门   (Device ID / 证书 / Claim Code / project tag)
        ↓
② 服务端认领+授权 (校验身份、匹配租户/项目、签发 token 或下发配置)
        ↓
③ 才允许上报数据  (带 token 的 MQTT / HTTPS，服务端按租户路由存储)
```

**你现在缺的是第 ① 步。** 第 ② 步的服务端路由我已经写好了（`beacon_server.py` 按 pid 分流）。

## 六、推荐路线

| 阶段 | 做什么 | 成本 |
|---|---|---|
| **立刻可用**（单项目/单网段） | 跑 `beacon_server.py` + `projects.json` 里开 `default`，**固件不用动** | 零改动 |
| **多项目共存** | 应用 `beacon-project-id.patch.md`，每个项目固件烧各自的 `PROJECT_ID`，服务端按 pid 分流 | 固件改 3 处 |
| **跨网段 / 要上公网** | 放弃多播，改**设备预置云端接入地址 + Device Token**，服务端按 token 路由租户（类似阿里云一机一密） | 较大改造，但这是正解 |
| **极限简化** | 配网页面手动填 ip/port（现在就能做），不要"自动" | 零成本但不可扩展 |

## 七、与你现有问题的关系

之前 `https://8ee1630c307b-0.hotyuo161.fnos.net` 那条路走不通，本质是**缺了第 ② 步的身份**：
FN Connect 只认你的浏览器会话，设备拿不到凭证。

而 **beacon 发现正好绕开了它**——整个握手发生在局域网内部，不需要穿透、不需要 https、
不需要公网身份。设备在内网拿到 IP/端口/账号后直接上报，**这是当前最干净的一条路**。
